# Adsterra public-page placement coverage audit

Local audit date: 2026-10-19. This is a placement and request audit, not an impression or revenue report. No production deployment or advertising-account change was made.

## Scope and eligibility

The generated sitemap has **109 public URLs**, but the current publication policy permits ads on **100** of them: the homepage, 81 production-ready tools, and 18 guides/categories. The other nine public URLs (`/help/`, `/about/`, `/careers/`, `/security/`, `/privacy-policy/`, `/terms/`, `/gdpr/`, `/guides/`, `/editorial-standards/`) are intentionally ad-free. Fourteen additional noindex tool routes are also ad-free and are outside the 109-URL sitemap. Calling all 109 URLs ad-eligible would contradict the current policy; this audit did not loosen it.

The reproducible route-level evidence is generated by `node tests/ad-coverage-browser.mjs [390|1024|1920]` into ignored local `test-results/ad-coverage/results-<width>.json`. Every eligible URL was loaded directly at each of those widths. The controlled test adapter replaces provider responses, so it validates planned placement, rendered container, exact request URL, collapse/remount behavior and geometry, **not actual Adsterra fill**.

The middle count includes the homepage and 18 guide/category Native placements. The after-tool count covers all 81 eligible tools, including Background Remover. There were zero request-count mismatches, duplicate unit URLs per page, page JavaScript errors, or body-width overflows in these three full-route fixture passes. The mobile pass needed one transient navigation retry and the tablet pass needed two; each route ultimately loaded and passed.

Per-page planned slot counts at 1920px: **33 long, rail-safe tools have six**; **47 other tools have three**; **Background Remover and 18 guide/category pages have one each**; **the homepage has two**. At 1024px, 80 tools have three, Background Remover has one, the homepage has two, and 18 guides/categories have one. At 390px, 80 tools and the homepage have two, while Background Remover and 18 guides/categories have one. The nine public policy-excluded URLs have zero. This is a maximum plan; no-fill, runtime suppression, smaller available width, or an interaction state can reduce visible ads.

On sufficiently long rail-safe desktop tools the six positions are: top horizontal, left rail, right rail, after-workspace, between guide sections, and lower in the guide. The additional lower placement requires at least four guide sections, substantial text on both sides, and a 320px inline width. It is never added to editors, tablets, phones or short guides. At 1280-1599px the missing left gutter reduces the maximum to five. The seventh optional footer-area placement was deliberately not added: the current inventory has one Native container and unique fixed IDs, so forcing another unit would either duplicate a provider ID or crowd the page. No empty area is reserved for it.

## What was and was not observed

- **Configured format:** all seven display units are centrally available, but each page uses only a responsive subset.
- **Rendered container:** the 100-route fixture produced 360/261/181 mounted test containers at 1920/1024/390px. Those are test mounts, not paid creatives.
- **Provider request:** the fixture observed the matching 360/261/181 exact approved loader URLs. A separate non-mocked local Chrome sample of `/compress-pdf/` at both 1600px and 1920px sent six real Adsterra loader requests per run, with no request failure or page error.
- **Actual creative displayed:** **zero of six** in each local real-provider sample. All six slots ended `empty` and collapsed to zero geometry. The 1920px screenshot at `test-results/ad-coverage/real-provider-compress-pdf-1920.png` shows the uploader and guide remain usable with no blank reserved ad blocks. A loader response or an iframe-shaped fixture is not counted as a real creative.

The local sample cannot establish whether the external outcome is inventory no-fill, local-origin eligibility, provider-side filtering, or another external condition. No production creative-fill rate has been measured. Do not infer earnings or impressions from these results.

## Interaction safety and rollout status

The 111-check responsive layout suite passed across nine representative tools and 320-2400px widths. It checked rail exclusions for Edit PDF and Crop Image, no workspace overlap, no horizontal overflow, one request per key, hidden/collapsed no-fill slots, and a real Compress PDF upload, process, download and PDF reopen. The full-route fixture also found no slot inside an active workspace. No ad is placed inside upload, editor, result or download controls. `npm run lint`, `npm test`, `npm run build`, `npm run test:ads:layout:browser`, and `npm run test:ads:browser` passed; the isolated PostgreSQL integration remains opt-in and was not run as part of this ad audit.

**Six-placement target: implemented for 33 sufficiently long, rail-safe desktop tools. Seven-placement option: pending by design, not forced.** Actual creative fill remains unverified on production and was absent in the local provider sample. Before any later deployment, review the placement screenshots at a real approved preview/production origin and confirm provider fill and creative suitability without changing the ad-free publication policy.
