# GXA Toolbox database recovery — root-cause report

Audit date: 2026-10-18  
Scope: read-only inspection of the local repository, GitHub `main`, public production endpoints, and the user-reported new Netlify database state.

## Executive finding

The application does not use `database.sql` in Netlify. That file is a destructive MySQL/Hostinger-era artifact (`CREATE DATABASE`, backticks, `ENUM`, `AUTO_INCREMENT`, `DROP TABLE`, seed rows) and is not safe or compatible with the current PostgreSQL runtime.

The live application uses `@netlify/database` 1.1.0 from Netlify Functions and queries explicitly qualified `public.*` PostgreSQL tables. The repository already has seven valid Netlify migrations in `netlify/database/migrations`. All seven applied successfully, in order, against an isolated `@netlify/database-dev` database during this audit and created the 12 expected tables. Therefore, a new production branch with zero `public` tables indicates a deployment/linkage/migration-application problem, not an absent schema design.

The most likely immediate cause is that the new Netlify project/database was provisioned but has not published a deploy that discovers and applies this repository's migrations, or the production deploy is not linked to the database branch reported in the explorer. The checkout itself has no linked site (`.netlify/state.json` is `{}`) and no database-related environment variables, so the new remote branch and non-public schemas cannot be queried safely from this machine. Do not add credentials to frontend code or grant a broad personal token to work around that boundary.

### Reconciliation with the confirmed production deploy log

The new log proves that the deploy scanner found migrations `0001`-`0007`, but "No pending database migrations" means the migration registry associated with that deploy already considers those names applied. That result is incompatible with an actually empty `public` schema on the same database unless the schema was later removed or the migration registry was imported/restored independently. The remaining alternatives are therefore:

1. **Database/branch mismatch (most likely):** the explorer and deployed Function runtime refer to different site/database branches.
2. **Migration-history/schema drift:** `netlify.migrations` on the runtime database contains `0001`-`0007`, while the expected `public` objects are absent.
3. **Stale/permission-limited explorer view:** less likely, but possible until the same runtime connection is queried.

The background-remover package/base path is not the cause: the log loaded root `netlify.toml` and discovered the root migration directory. A successful static build is not database proof.

## Exact database client and schema

- Client: `@netlify/database` `^1.1.0`, instantiated by `getDatabase()` in `netlify/functions/_database.mjs`.
- Local isolated engine: `@netlify/database-dev` `^0.10.1`.
- Query style: server-side tagged SQL; no browser database connection.
- Application schema: explicitly `public`.
- Netlify migration tracking schema/table: `netlify.migrations`.
- Expected public tables (12):
  - `users`
  - `user_profiles`
  - `file_jobs`
  - `tool_analytics_events`
  - `auth_events`
  - `system_events`
  - `support_messages`
  - `admin_profiles`
  - `admin_audit_events`
  - `admin_rate_limits`
  - `admin_resource_reads`
  - `support_message_notes`
- Trigger function: `public.gxa_set_updated_at()`.
- Migrations found: `0001` through `0007`. They are ordered, PostgreSQL-compatible, and apply cleanly to a fresh isolated database.

The application contains no query to an application table outside `public`. The only other expected schema reference is Netlify's own `netlify.migrations`. Whether a remote branch contains expected table names in another schema remains unverified until the authenticated diagnostic endpoint is run on a preview deploy.

## Diagnostic limitations found

The existing categorizer recognizes missing configuration, invalid credentials/database, missing table/column, and a generic query failure. It does not separately classify network endpoint failure, permission denial, capacity/startup unavailability, or expected tables located in a different schema. `admin-data` consequently reduces several distinct causes to "Database unavailable."

The patch adds an admin-authenticated, read-only function at `/.netlify/functions/admin-database-diagnostics`. It reports only status, expected table names/counts, missing tables, expected names found in other schemas, and migration names. It never returns credentials, rows, file metadata, user data, or SQL errors.

## Additional test drift

`tests/postgres-auth-integration.mjs` still hardcodes migrations `0001`-`0005`, although `0006` and `0007` exist. Therefore `RUN_POSTGRES_INTEGRATION=true` currently fails its migration-name assertion before functional assertions. The normal build skips this opt-in test. The recovery patch has its own isolated migration and contract checks; update the integration test's expected migration list when integrating the patch.

**19 October follow-up:** the integration test now discovers migration filenames, applies 0001–0008 in an isolated Netlify development database, and passes Identity profile, history, support, and admin analytics checks. The paragraph above describes the earlier audit state; it is not a current test failure. The production branch/linkage uncertainty remains until a protected preview diagnostic is run against the new Netlify site.
